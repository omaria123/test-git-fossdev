# Автоматизация разработки Python-проекта с использованием Make

## Введение

В современной разработке программного обеспечения важную роль играет автоматизация задач: создание изолированного окружения, управление зависимостями, проверка качества кода. Данный проект демонстрирует подход, при котором Make выступает единой точкой входа для всех операций, связанных с разработкой, тестированием и контролем качества кода.

Основная цель - показать, как стандартные инструменты Python (mypy, black, flake8) могут быть интегрированы в воспроизводимый процесс, а Makefile становится не просто набором команд, а системой композиции взаимосвязанных действий.

---

## Архитектура решения

Работа выполнена в ветке feature/make-automation.

Проект организован как монорепозиторий, в котором код, конфигурации и инструменты автоматизации объединены в единой структуре. 
Ключевой принцип - stateless окружение: все зависимости и инструменты устанавливаются в локальное виртуальное окружение .venv, а Makefile обращается к ним через абсолютные пути, что исключает необходимость ручной активации и гарантирует воспроизводимость на любой машине.

### Структура репозитория

В корне проекта расположены следующие файлы и директории:

- .gitignore - исключает из системы контроля версий виртуальное окружение, кэш-файлы Python, временные файлы инструментов;
- Makefile - главный файл автоматизации, содержащий все targets для управления проектом;
- README.md - документация, описывающая решение и инструкции по работе;
- requirements.txt - список зависимостей проекта и инструментов разработки;
- mypy.ini - конфигурация статического анализатора типов;
- pyproject.toml - общая конфигурация для black и flake8.

Директория scripts содержит вспомогательные скрипты, в частности check_requirements.py — скрипт для анализа импортов и проверки соответствия requirements.txt.

Директория src содержит исходный код проекта:
- app.py - точка входа приложения, использующая библиотеку requests;
- calc.py  модуль с математическими функциями, демонстрирующий аннотации типов;
- service.py - сервисный модуль с импортами requests, numpy и fastapi;
- example.py - демонстрационный файл с намеренными нарушениями стиля кода.

## Логика работы Makefile

Makefile построен таким образом: каждый target решает одну конкретую задачу, а сложные действия собираются из простых через систему зависимостей. Имена targets описывают действие, а не используемый инструмент - это позволяет изменять реализацию, не меняя интерфейс.

### Управление окружением

Виртуальное окружение создается в директории .venv. Все вызовы Python и инструментов идут через явные пути:

- PYTHON = .venv/bin/python
- PIP = .venv/bin/pip
- MYPY = .venv/bin/mypy
- BLACK = .venv/bin/black
- FLAKE8 = .venv/bin/flake8

Это решает проблему, связанную с тем, что Make запускает каждую строку target в отдельном shell-процессе, и традиционная активация окружения (source .venv/bin/activate) не сохраняется между строками.

### Доступные targets

В проекте реализованы следующие команды Make:

- make setup - создание виртуального окружения .venv, обновление pip, установка всех зависимостей из requirements.txt;
- make run - запуск приложения src/app.py через интерпретатор из виртуального окружения;
- make clean - удаление виртуального окружения .venv, всех директорий __pycache__ и файлов .pyc;
- make check-requirements - проверка, что все импорты в коде присутствуют в requirements.txt;
- make typecheck - статическая проверка типов с использованием mypy;
- make format - автоматическое форматирование кода с помощью black (все файлы);
- make format FILE=путь - форматирование одного указанного файла;
- make lint - проверка соответствия кода стандартам с помощью flake8;
- make check - композитный target, запускающий последовательно typecheck, check-requirements и lint.

## Реализация требований задания

### 1. Управление окружением (stateless)

Требование: каталог .venv внутри проекта, установка зависимостей в это окружение, target в Makefile, использующий окружение без активации.

Реализация: target setup создает виртуальное окружение через python3 -m venv .venv. Зависимости устанавливаются через вызов $(PIP) install -r requirements.txt. Target run вызывает $(PYTHON) src/app.py - прямой путь к интерпретатору в виртуальном окружении. Директория .venv добавлена в .gitignore, что соответствует принципу stateless: окружение не хранится в репозитории и создается заново на каждой машине.

### 2. Проверка зависимостей

Требование: анализ импортов в коде и сравнение с requirements.txt.

Реализация: создан скрипт scripts/check_requirements.py, который с помощью модуля ast парсит все Python-файлы в директории src и извлекает имена импортируемых модулей. Скрипт игнорирует модули из стандартной библиотеки Python. Сравнение происходит с именами пакетов из requirements.txt (без учета версий). Target check-requirements запускает этот скрипт через $(PYTHON). В случае обнаружения импорта, отсутствующего в requirements.txt, скрипт завершается с ошибкой, и make фиксирует это.

### 3. Проверка типов

Требование: внедрение статической проверки типов, target с именем, описывающим действие, а не инструмент.

Реализация: mypy добавлен в requirements.txt. Создан конфигурационный файл mypy.ini с минимальными настройками: указана версия Python (3.9), для библиотек без аннотаций типов (requests, numpy, fastapi) отключена проверка импортов с помощью ignore_missing_imports. Target typecheck запускает mypy для всех файлов в директории src с указанием конфигурационного файла. В коде src/calc.py была намеренно допущена ошибка типов (передача строки в функцию add, ожидающую целое число), которая обнаружена mypy и исправлена.

### 4. Проверка стилей

Требование: создание target для форматирования и проверки стиля, с именами, независимыми от конкретных инструментов.

Реализация: в requirements.txt добавлены black (автоматическое форматирование) и flake8 (проверка стиля). Создан файл pyproject.toml с общими настройками: максимальная длина строки установлена в 88 символов, что согласовано между black и flake8; отключены правила flake8, конфликтующие с black (E203, W503). Target format запускает black с возможностью указать конкретный файл через переменную FILE. Target lint запускает flake8 с указанием конфигурационного файла. Демонстрационный файл src/example.py содержит намеренные нарушения стиля (лишние пробелы, неправильные отступы), которые обнаруживаются при выполнении make lint и исправляются при выполнении make format.

### 5. Цепочки

Требование: составной target, объединяющий несколько проверок через систему зависимостей Make.

Реализация: создан target check, который в списке зависимостей перечисляет три других target: typecheck, check-requirements и lint. Make обрабатывает зависимости последовательно: сначала выполняется typecheck, затем check-requirements, затем lint. Если любой из этих targets завершается с ошибкой, выполнение make check прерывается, и ошибка фиксируется. Это демонстрирует, как из простых, переиспользуемых частей собирается сложный процесс контроля качества.

## Результаты работы

### Установка окружения и запуск приложения

При выполнении make setup создается виртуальное окружение и устанавливаются все зависимости, включая requests, numpy, fastapi, mypy, black и flake8. После успешной установки команда make run запускает приложение.

### Проверка зависимостей

Команда make check-requirements анализирует все импорты в файлах src и сравнивает их с требованиями. Результат успешной проверки: All imports match requirements.txt. Если бы в коде использовалась библиотека, не указанная в requirements.txt, скрипт вывел бы список отсутствующих зависимостей и завершился с ошибкой.

### Проверка типов

До исправления ошибки в calc.py команда make typecheck выдавала сообщение об ошибке: "Argument 2 to add has incompatible type str; expected int". После исправления (замена строки 3 на целое число) проверка проходит успешно.

### Проверка стиля

До форматирования команда make lint обнаруживает в example.py несколько нарушений: неправильное количество пустых строк, лишние пробелы после скобок, отсутствие пробелов после запятой, смешивание пробелов и табуляции в отступах. Команда make format автоматически исправляет все эти нарушения. После форматирования повторный запуск make lint завершается с сообщением "All done!".

### Композитная проверка

Команда make check последовательно запускает все три проверки. Если в коде есть проблемы проверки укажут на них. Это демонстрирует, что система проверок работает и выявляет проблемы.

Во-вторых, создана автоматизированная проверка зависимостей: скрипт анализирует импорты в коде и сравнивает их с объявленными в requirements.txt.

В-третьих, внедрена статическая проверка типов с помощью mypy: обнаружена и исправлена ошибка типов, создан target typecheck с именем, описывающим действие, а не инструмент.

В-четвертых, добавлены инструменты форматирования и линтинга: black и flake8 интегрированы через targets format и lint.

В-пятых, построена цепочка проверок: target check объединяет все три проверки через систему зависимостей Make, демонстрируя композицию простых действий в сложный процесс.

Все действия автоматизированы, воспроизводимы и не зависят от системного окружения.
